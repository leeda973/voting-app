`HEAD`와 사용자가 제시한 고정 지점 사이의 diff에 대한 2축 리뷰:

- **Standards**: 코드가 이 저장소에 문서화된 코딩 표준을 따르는가?
- **Spec**: 코드가 원래 이슈 / 스펙을 충실하게 구현하는가?

두 축은 서로의 컨텍스트를 오염시키지 않도록 **병렬 서브에이전트**로 실행되며, 그 후 이 스킬이 결과를 취합한다.

이슈 트래커 정보는 이미 제공되었어야 한다. `docs/agents/issue-tracker.md`가 없다면 사용자에게 `/setup-matt-pocock-skills`를 실행하라고 알려라.

## 프로세스

### 1. 고정 지점 확정

사용자가 말한 것이 무엇이든 그것이 고정 지점이다(커밋 SHA, 브랜치 이름, 태그, `main`, `HEAD~5` 등). 지정하지 않았다면 물어보라.

diff 명령은 한 번만 정해 둔다: `git diff <fixed-point>...HEAD` (점 세 개. 따라서 merge-base와 비교된다). `git log <fixed-point>..HEAD --oneline`으로 커밋 목록도 기록해 둔다.

더 진행하기 전에 고정 지점이 해석되는지(`git rev-parse <fixed-point>`), 그리고 diff가 비어 있지 않은지 확인하라. 잘못된 ref나 빈 diff는 두 병렬 서브에이전트 안이 아니라 여기서 실패해야 한다.

### 2. 스펙 출처 파악

원래 스펙을 다음 순서로 찾는다:

1. 커밋 메시지의 이슈 참조(`#123`, `Closes #45`, GitLab `!67` 등). `docs/agents/issue-tracker.md`의 워크플로로 가져온다.
2. 사용자가 인자로 넘긴 경로.
3. `docs/`, `specs/`, `.scratch/` 아래에서 브랜치 이름이나 기능과 일치하는 스펙 파일.
4. 아무것도 찾지 못했다면 사용자에게 스펙이 어디 있는지 물어보라. 없다고 하면 **Spec** 서브에이전트는 건너뛰고 "no spec available"(사용 가능한 스펙 없음)이라고 보고한다.

### 3. 표준 출처 파악

코드를 어떻게 작성해야 하는지 문서화한 저장소 내의 모든 것. 예: `CODING_STANDARDS.md`, `CONTRIBUTING.md`.

저장소가 문서화한 것에 더해, Standards 축은 항상 아래의 **스멜 기준선(smell baseline)** 을 포함한다. 저장소가 아무것도 문서화하지 않았어도 적용되는 Fowler의 코드 스멜 고정 목록이다(_Refactoring_, 3장). 두 가지 규칙이 적용된다:

- **저장소가 우선한다.** 문서화된 저장소 표준이 항상 이긴다. 기준선이 지적할 무언가를 저장소 표준이 승인한다면 그 스멜은 억제하라.
- **항상 판단의 문제다.** 각 스멜은 명확한 위반이 아니라 이름 붙은 휴리스틱("possible Feature Envy")이다. 여기의 다른 표준과 마찬가지로, 도구가 이미 강제하는 것은 건너뛰어라.

각 스멜은 *무엇인지* → *어떻게 고치는지* 순으로 읽는다. diff와 대조하라:

- **Mysterious Name(수수께끼 같은 이름)**: 무엇을 하는지 또는 무엇을 담는지 이름이 드러내지 않는 함수, 변수, 타입. → 이름을 바꿔라. 정직한 이름이 떠오르지 않는다면 설계가 흐릿한 것이다.
- **Duplicated Code(중복 코드)**: 같은 로직 형태가 변경 내 둘 이상의 헝크나 파일에 나타난다. → 공통 형태를 추출하고 양쪽에서 호출하라.
- **Feature Envy(기능 욕심)**: 자기 데이터보다 다른 객체의 데이터에 더 많이 손을 뻗는 메서드. → 메서드를 그것이 탐내는 데이터 쪽으로 옮겨라.
- **Data Clumps(데이터 뭉치)**: 같은 몇 개의 필드나 매개변수가 계속 함께 다닌다(태어나고 싶어 하는 타입). → 하나의 타입으로 묶어서 그것을 넘겨라.
- **Primitive Obsession(기본형 집착)**: 자체 타입을 가질 만한 도메인 개념을 기본형이나 문자열이 대신하고 있다. → 그 개념에 작은 전용 타입을 줘라.
- **Repeated Switches(반복되는 스위치)**: 같은 타입에 대한 같은 `switch`/`if` 연쇄가 변경 전반에 반복된다. → 다형성으로, 또는 두 곳이 공유하는 하나의 맵으로 대체하라.
- **Shotgun Surgery(산탄총 수술)**: 하나의 논리적 변경 때문에 diff 내 여러 파일에 흩어진 수정이 필요하다. → 함께 바뀌는 것들을 하나의 모듈로 모아라.
- **Divergent Change(뒤엉킨 변경)**: 하나의 파일이나 모듈이 서로 관련 없는 여러 이유로 수정된다. → 각 모듈이 하나의 이유로만 바뀌도록 나눠라.
- **Speculative Generality(추측성 일반화)**: 스펙에 없는 필요를 위해 추가된 추상화, 매개변수, 훅. → 삭제하라. 실제 필요가 나타날 때까지 다시 인라인하라.
- **Message Chains(메시지 체인)**: 호출자가 의존해서는 안 되는 긴 `a.b().c().d()` 탐색. → 그 탐색을 첫 번째 객체의 메서드 하나 뒤에 숨겨라.
- **Middle Man(중개자)**: 대부분 그저 다음으로 위임만 하는 클래스나 함수. → 잘라 내고 실제 대상을 직접 호출하라.
- **Refused Bequest(상속 거부)**: 상속받은 것의 대부분을 무시하거나 오버라이드하는 서브클래스나 구현체. → 상속을 버리고 합성을 사용하라.

### 4. 두 서브에이전트를 병렬로 실행

**Standards 서브에이전트 프롬프트**에는 다음이 포함되어야 한다:

- 전체 diff 명령과 커밋 목록.
- 3단계에서 찾은 표준 출처 파일 목록, **그리고 3단계의 스멜 기준선** 전문(서브에이전트는 다른 방법으로 이것에 접근할 수 없다).
- 지시: "관련 있는 경우 파일/헝크별로 다음을 보고하라. (a) diff가 문서화된 표준을 위반하는 모든 곳: 해당 표준을 인용하라(파일 + 규칙). (b) 발견한 기준선 스멜: 이름을 대고 헝크를 인용하라. 명확한 위반과 판단의 문제를 구분하라. 문서화된 표준 위반은 명확한 위반일 수 있지만, 기준선 스멜은 항상 판단의 문제이며, 문서화된 저장소 표준이 기준선보다 우선한다. 도구가 강제하는 것은 건너뛰어라. 400단어 이내."

**Spec 서브에이전트 프롬프트**에는 다음이 포함되어야 한다:

- diff 명령과 커밋 목록.
- 스펙의 경로 또는 가져온 내용.
- 지시: "다음을 보고하라. (a) 스펙이 요구했지만 누락되었거나 부분적인 요구 사항. (b) 요구되지 않았는데 diff에 있는 동작(범위 확장). (c) 구현된 것처럼 보이지만 구현이 잘못된 것 같은 요구 사항. 각 발견 사항마다 스펙의 해당 줄을 인용하라. 400단어 이내."

스펙이 없다면 Spec 서브에이전트는 건너뛰고 최종 보고서에 그 사실을 적어라.

### 5. 취합

두 보고서를 `## Standards`와 `## Spec` 제목 아래에 그대로 또는 가볍게 다듬어서 제시하라. 두 축은 의도적으로 분리되어 있으므로 발견 사항을 합치거나 순위를 다시 매기지 **마라** (_왜 두 축인가_ 참고).

한 줄 요약으로 끝내라. 축별 발견 사항 총수와, _각 축 안에서_ 가장 심각한 문제(있다면). 축을 가로질러 하나의 승자를 고르지 마라. 그것이 바로 이 분리가 막으려는 순위 재조정이다.

## 왜 두 축인가

변경은 한 축은 통과하고 다른 축은 실패할 수 있다:

- 모든 표준을 따르지만 엉뚱한 것을 구현한 코드 → **Standards 통과, Spec 실패.**
- 이슈가 요구한 것을 정확히 하지만 프로젝트의 관례를 깨는 코드 → **Spec 통과, Standards 실패.**

두 축을 따로 보고하면 한 축이 다른 축을 가리는 일을 막을 수 있다.
