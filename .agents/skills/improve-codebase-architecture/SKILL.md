# 코드베이스 아키텍처 개선

아키텍처상의 마찰을 드러내고 **심화 기회(deepening opportunity)**, 즉 얕은(shallow) module을 깊은(deep) module로 바꾸는 리팩터링을 제안하세요. 목표는 테스트 용이성과 AI 탐색 용이성(AI-navigability)입니다.

이 명령은 프로젝트의 도메인 모델을 _바탕으로_ 하며, 공통 설계 어휘 위에 구축되어 있습니다.

- 아키텍처 어휘(**module**, **interface**, **depth**, **seam**, **adapter**, **leverage**, **locality**)와 그 원칙(삭제 테스트(deletion test), "interface가 곧 테스트 표면이다", "adapter가 하나면 가상의 seam, 둘이면 실제 seam")을 위해 Skill 도구를 "codebase-design"으로 호출하세요. 모든 제안에서 이 용어들을 정확히 그대로 사용하고, "component", "service", "API", "boundary" 같은 말로 흐르지 마세요.
- `CONTEXT.md`의 도메인 언어는 좋은 seam에 이름을 부여합니다. `docs/adr/`의 ADR에는 이 명령이 다시 논쟁해서는 안 되는 결정들이 기록되어 있습니다.

## 절차

### 1. 탐색

**스캔하기 전에 범위를 정하세요: YAGNI.** module을 심화하면 이후의 변경이 쉬워지는 것으로 보상받으므로, 최근에 변경된 코드베이스 부분에 가중치를 더 두세요. 살펴보기 전에 _어디를_ 볼지 정하세요.

- 사용자가 방향(module, 하위 시스템, 불편한 지점)을 지정했다면 그것을 따르고, 아래의 추론은 건너뛰세요.
- 그렇지 않다면 커밋 기록(`git log --oneline`)을 충분히 거슬러 올라가 코드베이스의 핫스팟, 즉 계속 등장하는 파일과 영역을 찾고, 그 경로들에 먼저 주의를 기울이세요. 변경이 뚜렷한 핫스팟 없이 흩어져 있다면 범위를 넓히세요.

먼저 프로젝트의 도메인 용어집(`CONTEXT.md`)과 작업하려는 영역의 ADR을 읽으세요.

그런 다음 서브에이전트를 띄워 코드베이스를 둘러보게 하세요. 경직된 휴리스틱을 따르지 말고, 유기적으로 탐색하며 마찰을 느끼는 지점을 기록하세요.

- 하나의 개념을 이해하기 위해 여러 작은 module 사이를 오가야 하는 곳은 어디인가?
- interface가 implementation만큼이나 복잡한 **shallow** module은 어디인가?
- 테스트 용이성만을 위해 순수 함수를 추출했지만, 실제 버그는 그것을 호출하는 방식에 숨어 있는 곳(**locality** 없음)은 어디인가?
- 강하게 결합된 module들이 seam을 넘어 새어 나가는 곳은 어디인가?
- 코드베이스에서 테스트되지 않았거나, 현재 interface로는 테스트하기 어려운 부분은 어디인가?

shallow하다고 의심되는 것에는 **삭제 테스트(deletion test)**를 적용하세요. 그것을 삭제하면 복잡성이 한곳에 모이는가, 아니면 그저 다른 곳으로 옮겨 가는가? "예, 모인다"가 당신이 찾는 신호입니다.

### 2. 후보를 HTML 보고서로 제시하기

리포지토리에 아무것도 남지 않도록 OS 임시 디렉터리에 자체 완결형 HTML 파일을 작성하세요. 임시 디렉터리는 `$TMPDIR`에서 확인하고, 없으면 `/tmp`(Windows에서는 `%TEMP%`)를 사용하세요. 매 실행마다 새 파일이 생기도록 `<tmpdir>/architecture-review-<timestamp>.html`에 작성하세요. 사용자를 위해 파일을 열고(Linux에서는 `xdg-open <path>`, macOS에서는 `open <path>`, Windows에서는 `start <path>`) 절대 경로를 알려 주세요.

보고서는 레이아웃과 스타일링에 **CDN을 통한 Tailwind**를, 그래프/흐름/시퀀스가 구조를 확실하게 전달하는 경우의 다이어그램에 **CDN을 통한 Mermaid**를 사용합니다. Mermaid와 직접 만든 CSS/SVG 시각 자료를 섞어 쓰세요. 관계가 그래프 형태(호출 그래프, 의존성, 시퀀스)일 때는 Mermaid를, 좀 더 편집적인 표현(질량 다이어그램, 단면도, 접힘 애니메이션)을 원할 때는 직접 만든 div/SVG를 사용하세요. 각 후보에는 **이전/이후 시각화**가 들어갑니다. 시각적으로 표현하세요.

각 후보마다 다음을 담은 카드를 렌더링하세요.

- **파일**: 관련된 파일/module
- **문제**: 현재 아키텍처가 왜 마찰을 일으키는지
- **해결책**: 무엇이 바뀌는지에 대한 쉬운 설명
- **이점**: locality와 leverage 관점의 설명, 그리고 테스트가 어떻게 개선되는지
- **이전 / 이후 다이어그램**: 나란히 배치하고 직접 그려서, shallow함과 심화를 보여 주는 그림
- **추천 강도**: `Strong`, `Worth exploring`, `Speculative` 중 하나로, 배지로 렌더링

보고서는 **최우선 추천** 섹션으로 마무리하세요. 어떤 후보를 가장 먼저 다룰지와 그 이유를 적습니다.

**도메인에는 CONTEXT.md 어휘를, 아키텍처에는 `/codebase-design` 어휘를 사용하세요.** `CONTEXT.md`가 "Order"를 정의한다면 "FooBarHandler"나 "Order service"가 아니라 "Order intake module"이라고 말하세요.

**ADR 충돌**: 후보가 기존 ADR과 모순된다면, 그 ADR을 재검토할 만큼 마찰이 실제로 클 때만 제시하세요. 카드에 명확히 표시하세요(예: 경고 콜아웃 _"ADR-0007과 모순되지만, …때문에 다시 열어 볼 가치가 있음"_). ADR이 금지하는 이론상의 리팩터링을 모두 나열하지는 마세요.

전체 HTML 뼈대, 다이어그램 패턴, 스타일링 지침은 [HTML-REPORT.md](HTML-REPORT.md)를 참고하세요.

아직 interface를 제안하지 마세요. 파일을 작성한 뒤 사용자에게 "이 중 어떤 것을 탐색해 보고 싶으신가요?"라고 물어보세요.

### 3. Grilling 루프

사용자가 후보를 고르면 Skill 도구를 "grilling"으로 호출해 사용자와 함께 결정 트리를 따라가세요. 제약 조건, 의존성, 심화된 module의 형태, seam 뒤에 무엇이 놓이는지, 어떤 테스트가 살아남는지 등을 다룹니다.

부수 작업은 결정이 구체화되는 대로 그 자리에서 처리합니다. 진행하면서 도메인 모델을 최신 상태로 유지하려면 Skill 도구를 "domain-modeling"으로 호출하세요.

- **`CONTEXT.md`에 없는 개념의 이름을 심화된 module에 붙이나요?** 그 용어를 `CONTEXT.md`에 추가하세요. 파일이 없다면 필요할 때 만드세요.
- **대화 중에 모호한 용어를 다듬었나요?** 그 자리에서 `CONTEXT.md`를 업데이트하세요.
- **사용자가 핵심적인 이유로 후보를 거절하나요?** ADR 작성을 제안하되, _"이후의 아키텍처 리뷰에서 다시 제안되지 않도록 이것을 ADR로 기록해 둘까요?"_라는 식으로 제안하세요. 같은 것을 다시 제안하지 않기 위해 이후의 탐색자가 실제로 그 이유를 알아야 할 때만 제안하고, 일시적인 이유("지금은 할 가치가 없음")나 자명한 이유는 건너뛰세요.
- **심화된 module의 대안 interface를 탐색하고 싶나요?** Skill 도구를 "codebase-design"으로 호출하고, 그 스킬의 design-it-twice 병렬 서브에이전트 패턴을 사용하세요.
