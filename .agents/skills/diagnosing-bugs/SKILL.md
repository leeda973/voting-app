# Diagnosing Bugs

어려운 버그를 위한 규율. 명시적으로 정당화될 때만 페이즈를 건너뛰어라.

코드베이스를 탐색할 때는 `CONTEXT.md`(있다면)를 읽어 관련 모듈에 대한 명확한 멘탈 모델을 잡고, 손대는 영역의 ADR을 확인하라.

## 민감 정보 삭제

이 스킬은 명령, 출력, 캡처한 산출물을 보여 주게 한다. **먼저 모든 시크릿을 삭제하라**: 그 자리에 `<REDACTED>`라고 써라. 루프는 환경 변수를 기준으로 만들어서, 자격 증명이 보여 주는 내용이 아니라 환경 안에 머물게 하라. 캡처한 산출물에는 인증 헤더가 들어 있다. 신호를 담은 줄만 인용하라.

삭제된 출력만으로 버그를 진단하기에 부족하다면, 그렇다고 말하고 사용자에게 물어보라.

## 페이즈 1: 피드백 루프 만들기

**이것이 이 스킬의 핵심이다.** 나머지는 모두 기계적이다. 버그에 대한 **촘촘한(tight)** 통과/실패 신호(_이_ 버그에서 빨간불이 켜지는 신호)가 있다면 원인을 찾게 된다. 이분 탐색, 가설 검증, 계측은 모두 그 신호를 소비할 뿐이다. 그런 신호가 없다면 코드를 아무리 들여다봐도 구원받지 못한다.

여기에 불균형할 만큼 많은 노력을 쏟아라. **공격적으로. 창의적으로. 포기하지 마라.**

### 만드는 방법, 대략 이 순서로

1. 버그에 닿는 어떤 심(seam)에서든 **실패하는 테스트**: 단위, 통합, e2e.
2. 실행 중인 개발 서버에 대한 **Curl / HTTP 스크립트**.
3. 픽스처 입력으로 **CLI 호출**을 하고, stdout을 정상 스냅숏과 diff.
4. UI를 구동하고 DOM/콘솔/네트워크를 검증하는 **헤드리스 브라우저 스크립트**(Playwright / Puppeteer).
5. **캡처한 트레이스 재생.** 실제 네트워크 요청 / 페이로드 / 이벤트 로그를 디스크에 저장하고, 해당 코드 경로에서 격리된 상태로 재생한다.
6. **일회용 하니스(harness).** 함수 호출 하나로 버그 코드 경로를 실행하는, 시스템의 최소 부분집합(서비스 하나, 목 처리한 의존성)을 띄운다.
7. **속성 / 퍼즈 루프.** 버그가 "가끔 잘못된 출력"이라면, 무작위 입력 1000개를 실행하고 실패 양상을 찾아라.
8. **이분 탐색 하니스.** 두 알려진 상태(커밋, 데이터셋, 버전) 사이에 버그가 나타났다면, "상태 X로 부팅, 확인, 반복"을 자동화하여 `git bisect run`으로 돌릴 수 있게 하라.
9. **차분 루프(differential loop).** 같은 입력을 구버전과 신버전(또는 두 설정)에 통과시키고 출력을 diff하라.
10. **HITL bash 스크립트.** 최후의 수단. 사람이 클릭해야 한다면 `scripts/hitl-loop.template.sh`로 _그 사람을_ 구동하여 루프가 여전히 구조화되게 하라. 캡처된 출력은 당신에게 다시 전달된다.

올바른 피드백 루프를 만들면 버그는 90% 고쳐진 것이다.

### 루프 조이기

루프를 하나의 제품처럼 다뤄라. _일단_ 루프가 생기면 **조여라**:

- 더 빠르게 만들 수 있는가? (준비 과정 캐시, 무관한 초기화 생략, 테스트 범위 축소.)
- 신호를 더 날카롭게 만들 수 있는가? ("크래시 안 남"이 아니라 구체적인 증상을 검증.)
- 더 결정적으로 만들 수 있는가? (시간 고정, RNG 시드 지정, 파일 시스템 격리, 네트워크 동결.)

30초짜리 불안정한 루프는 루프가 없는 것보다 겨우 나은 수준이다. 2초짜리 결정적 루프는 촘촘하며, 디버깅의 초능력이다.

### 비결정적 버그

목표는 깔끔한 재현이 아니라 **더 높은 재현율**이다. 트리거를 100번 반복하고, 병렬화하고, 부하를 더하고, 타이밍 창을 좁히고, sleep을 주입하라. 50% 확률로 나타나는 버그는 디버깅할 수 있지만 1%는 그렇지 않으니, 디버깅할 수 있을 때까지 재현율을 계속 높여라.

### 정말로 루프를 만들 수 없을 때

멈추고 명시적으로 그렇게 말하라. 시도한 것을 나열하라. 사용자에게 다음을 요청하라: (a) 재현되는 환경에 대한 접근, (b) 민감 정보를 삭제한 캡처 산출물(HAR 파일, 로그 덤프, 코어 덤프, 타임스탬프가 있는 화면 녹화), 또는 (c) 임시 프로덕션 계측을 추가할 권한. 루프 없이 가설 단계로 넘어가지 **마라**.

### 완료 기준: 빨간불이 켜지는 촘촘한 루프

루프가 **촘촘하고** **빨간불을 낼 수 있을 때(red-capable)** 페이즈 1이 끝난다. **이미 최소 한 번 실행해 본** **명령 하나**(스크립트 경로, 테스트 호출, curl)를 댈 수 있어야 하며(호출과 그 출력을 민감 정보를 삭제하여 보여 줘라), 그 명령은 다음을 만족해야 한다:

- [ ] **빨간불 가능**: 실제 버그 코드 경로를 구동하고 **사용자가 말한 정확한 증상**을 검증하므로, 이 버그에서 빨간불이 켜지고 고쳐지면 초록불이 켜질 수 있다. "오류 없이 실행됨"이 아니다. _이 특정 버그를 잡아낼_ 수 있어야 한다.
- [ ] **결정적**: 매 실행마다 같은 판정(불안정한 버그: 위에서 말한 대로, 고정된 높은 재현율).
- [ ] **빠름**: 분이 아니라 초 단위.
- [ ] **에이전트 실행 가능**: 감독 없이 실행할 수 있다. 사람이 루프에 들어가는 것은 `scripts/hitl-loop.template.sh`를 통해서만.

이 명령이 존재하기 전에 이론을 세우려고 코드를 읽고 있는 자신을 발견하면, **멈춰라. 곧장 가설로 뛰어드는 것이 바로 이 스킬이 막으려는 실패다.** 빨간불을 낼 수 있는 명령이 없으면 페이즈 2도 없다.

## 페이즈 2: 재현 + 최소화

루프를 실행하라. 버그가 나타나면서 빨간불이 켜지는 것을 지켜보라.

확인하라:

- [ ] 루프가 근처에서 우연히 일어나는 다른 실패가 아니라 **사용자**가 설명한 실패 양상을 만들어 낸다. 버그가 틀리면 수정도 틀린다.
- [ ] 실패가 여러 번 실행해도 재현된다(비결정적 버그라면, 디버깅할 수 있을 만큼 높은 비율로 재현된다).
- [ ] 이후 페이즈에서 수정이 실제로 그것을 해결하는지 검증할 수 있도록 정확한 증상(오류 메시지, 잘못된 출력, 느린 타이밍)을 캡처했다.

### 최소화

빨간불이 켜지면 재현을 **여전히 빨간불이 켜지는 가장 작은 시나리오**로 줄여라. 입력, 호출자, 설정, 데이터, 단계를 **하나씩** 잘라 내고, 자를 때마다 루프를 다시 실행하며, 실패에 꼭 필요한 것만 남겨라.

왜 굳이 하는가: 최소 재현은 페이즈 3의 가설 공간을 줄이고(의심할 움직이는 부품이 줄어든다), 페이즈 5에서 깔끔한 회귀 테스트가 된다.

**남은 모든 요소가 꼭 필요할 때**, 즉 어느 하나를 제거해도 루프가 초록불이 될 때 끝난다.

재현**하고** 최소화할 때까지 진행하지 마라.

## 페이즈 3: 가설 세우기

어느 것이든 검증하기 전에 **순위를 매긴 가설 3–5개**를 만들어라. 가설을 하나만 만들면 처음 떠오른 그럴듯한 아이디어에 고정된다.

각 가설은 **반증 가능**해야 한다. 그 가설이 하는 예측을 명시하라.

> 형식: "<X>가 원인이라면, <Y를 바꾸면> 버그가 사라질 것이다 / <Z를 바꾸면> 더 나빠질 것이다."

예측을 명시할 수 없다면 그 가설은 느낌일 뿐이다. 버리거나 날카롭게 다듬어라.

**검증하기 전에 순위 목록을 사용자에게 보여 줘라.** 사용자는 즉시 순위를 바꿀 도메인 지식을 가지고 있거나("#3 관련 변경을 방금 배포했어요"), 이미 배제한 가설을 알고 있는 경우가 많다. 저렴한 체크포인트이자 큰 시간 절약이다. 여기서 막혀 있지는 마라. 사용자가 자리에 없다면(AFK) 자신의 순위대로 진행하라.

## 페이즈 4: 계측

각 탐침은 페이즈 3의 특정 예측에 대응해야 한다. **한 번에 변수 하나만 바꿔라.**

도구 선호 순서:

1. 환경이 지원한다면 **디버거 / REPL 검사**. 브레이크포인트 하나가 로그 열 개보다 낫다.
2. 가설들을 구분하는 경계에 **표적 로그**.
3. "전부 로그로 찍고 grep"은 절대 하지 마라.

**모든 디버그 로그에 태그를 붙여라.** 고유 접두사를 써라. 예: `[DEBUG-a4f2]`. 마지막 정리가 grep 한 번으로 끝난다. 태그 없는 로그는 살아남고, 태그 붙은 로그는 제거된다.

**성능 분기.** 성능 회귀에서는 대개 로그가 틀린 도구다. 대신 기준 측정(타이밍 하니스, `performance.now()`, 프로파일러, 쿼리 플랜)을 확립한 뒤 이분 탐색하라. 먼저 측정하고, 그다음 고쳐라.

## 페이즈 5: 수정 + 회귀 테스트

회귀 테스트는 **수정 전에** 작성하되, 그것을 위한 **올바른 심**이 있을 때만 작성하라.

올바른 심이란 테스트가 호출 지점에서 일어나는 그대로의 **실제 버그 패턴**을 실행하는 심이다. 사용 가능한 유일한 심이 너무 얕다면(버그에 여러 호출자가 필요한데 단일 호출자 테스트, 버그를 촉발한 연쇄를 재현할 수 없는 단위 테스트), 거기서의 회귀 테스트는 거짓 안심을 준다.

**올바른 심이 없다면, 그 자체가 발견이다.** 기록하라. 코드베이스 아키텍처가 버그를 가두지 못하게 막고 있는 것이다. 다음 페이즈를 위해 이것을 표시해 두라.

올바른 심이 있다면:

1. 최소화한 재현을 그 심에서 실패하는 테스트로 바꿔라.
2. 실패하는 것을 지켜보라.
3. 수정을 적용하라.
4. 통과하는 것을 지켜보라.
5. 원래의(최소화하지 않은) 시나리오에 대해 페이즈 1 피드백 루프를 다시 실행하라.

## 페이즈 6: 정리

완료를 선언하기 전에 필수:

- [ ] 원래 재현이 더 이상 재현되지 않는다(페이즈 1 루프를 다시 실행)
- [ ] 회귀 테스트가 통과한다(또는 심이 없다는 사실이 문서화되어 있다)
- [ ] 모든 `[DEBUG-...]` 계측이 제거되었다(접두사로 `grep`)
- [ ] 일회용 프로토타입이 삭제되었다(또는 명확히 표시된 디버그 위치로 옮겨졌다)
- [ ] 옳은 것으로 판명된 가설이 커밋 / PR 메시지에 명시되어, 다음에 디버깅하는 사람이 배울 수 있다
