# 에이전트 브리프 작성하기

에이전트 브리프는 GitHub 이슈나 PR이 `ready-for-agent`로 이동할 때 게시하는 구조화된 댓글이다. AFK 에이전트가 작업의 기준으로 삼는 권위 있는 명세다. 원래 본문과 토론은 맥락일 뿐이고, 에이전트 브리프가 계약이다.

브리프는 **에이전트가 무엇을 해야 하는지**를 명시하며, 이는 두 경우 모두에 해당한다. 이슈라면 변경을 처음부터 만드는 것이고, PR이라면 *기존 diff에 대해* 남은 일, 즉 마무리하고, 빈틈을 메우고, 리뷰 지적 사항을 처리하는 것이다. 원칙은 어느 쪽이든 같으며, 아래 PR 예시가 차이를 보여준다.

## 원칙

### 정밀함보다 지속성

이슈는 며칠이나 몇 주 동안 `ready-for-agent`에 머물 수 있다. 그동안 코드베이스는 바뀐다. 파일 이름이 바뀌거나, 이동되거나, 리팩터링되어도 유용하도록 브리프를 작성한다.

- 인터페이스, 타입, 동작 계약을 **기술한다**
- 에이전트가 찾거나 수정해야 할 구체적인 타입, 함수 시그니처, 설정 형태를 **명시한다**
- 파일 경로를 **언급하지 않는다**: 금방 낡는다
- 줄 번호를 **언급하지 않는다**
- 현재 구현 구조가 그대로 유지된다고 **가정하지 않는다**

### 절차가 아니라 동작

구현 **방법**이 아니라 시스템이 **무엇을** 해야 하는지 기술한다. 에이전트는 코드베이스를 새로 탐색하고 스스로 구현 결정을 내린다.

- **좋음:** "`SkillConfig` 타입은 `CronExpression` 타입의 선택적 `schedule` 필드를 받아야 한다"
- **나쁨:** "src/types/skill.ts를 열고 42번째 줄에 schedule 필드를 추가하라"
- **좋음:** "사용자가 인자 없이 `/triage`를 실행하면 주의가 필요한 이슈 요약을 볼 수 있어야 한다"
- **나쁨:** "메인 핸들러 함수에 switch 문을 추가하라"

### 완전한 인수 조건

에이전트는 언제 끝났는지 알아야 한다. 모든 에이전트 브리프에는 구체적이고 테스트 가능한 인수 조건(acceptance criteria)이 있어야 한다. 각 조건은 독립적으로 검증할 수 있어야 한다.

- **좋음:** "`gh issue list --label needs-triage`를 실행하면 초기 분류를 거친 이슈가 반환된다"
- **나쁨:** "트리아지가 올바르게 동작해야 한다"

### 명시적 범위 경계

무엇이 범위 밖인지 명시한다. 이렇게 하면 에이전트가 과도하게 손대거나(gold-plating) 인접 기능에 대해 가정하는 것을 막을 수 있다.

## 템플릿

```markdown
## 에이전트 브리프

**카테고리:** bug / enhancement
**요약:** 무엇이 이루어져야 하는지 한 줄 설명

**현재 동작:**
지금 무슨 일이 일어나는지 기술한다. 버그라면 고장난 동작이다.
enhancement라면 기능이 기반으로 삼는 현 상태다.

**원하는 동작:**
에이전트의 작업이 끝난 뒤 어떻게 되어야 하는지 기술한다.
엣지 케이스와 오류 상황을 구체적으로 적는다.

**핵심 인터페이스:**
- `TypeName`: 무엇을 왜 바꿔야 하는지
- `functionName()` 반환 타입: 현재 반환하는 것과 반환해야 하는 것
- 설정 형태: 필요한 새 설정 옵션

**인수 조건:**
- [ ] 구체적이고 테스트 가능한 조건 1
- [ ] 구체적이고 테스트 가능한 조건 2
- [ ] 구체적이고 테스트 가능한 조건 3

**범위 외:**
- 이 이슈에서 바꾸거나 다루면 안 되는 것
- 관련 있어 보이지만 별개인 인접 기능
```

## 예시

### 좋은 에이전트 브리프 (bug)

```markdown
## 에이전트 브리프

**카테고리:** bug
**요약:** 스킬 설명 자르기가 단어 중간에서 끊겨 깨진 출력을 만든다

**현재 동작:**
스킬 설명이 1024자를 넘으면 단어 경계와 상관없이 정확히 1024자에서
잘린다. 그 결과 설명이 단어 중간에서 끝난다
(예: "Use when the user wants to confi").

**원하는 동작:**
1024자 이전의 마지막 단어 경계에서 자르고, 잘렸음을 나타내도록
"..."를 붙여야 한다.

**핵심 인터페이스:**
- `SkillMetadata` 타입의 `description` 필드: 타입 변경은 필요 없지만,
  이를 채우는 검증/처리 로직이 단어 경계를 지켜야 한다
- SKILL.md frontmatter를 읽고 description을 추출하는 모든 함수

**인수 조건:**
- [ ] 1024자 미만 설명은 변경되지 않는다
- [ ] 1024자를 넘는 설명은 1024자 이전의 마지막 단어 경계에서
      잘린다
- [ ] 잘린 설명은 "..."로 끝난다
- [ ] "..."를 포함한 전체 길이가 1024자를 넘지 않는다

**범위 외:**
- 1024자 제한 자체를 바꾸는 것
- 여러 줄 설명 지원
```

### 좋은 에이전트 브리프 (enhancement)

```markdown
## 에이전트 브리프

**카테고리:** enhancement
**요약:** 거절된 기능 요청을 추적하기 위한 `.out-of-scope/` 디렉터리 지원 추가

**현재 동작:**
기능 요청이 거절되면 이슈는 `wontfix` 라벨과 댓글과 함께 닫힌다.
결정이나 근거에 대한 영구 기록이 없다. 이후 비슷한 요청이 오면
메인테이너가 이전 논의를 기억하거나 검색해야 한다.

**원하는 동작:**
거절된 기능 요청은 `.out-of-scope/<concept>.md` 파일에 문서화되어야 하며,
결정, 근거, 해당 기능을 요청한 모든 이슈 링크를 담아야 한다.
새 이슈를 트리아지할 때 이 파일들과 일치하는지 확인해야 한다.

**핵심 인터페이스:**
- `.out-of-scope/`의 마크다운 파일 형식: 각 파일에는
  `# Concept Name` 제목, `**Decision:**` 줄, `**Reason:**` 줄,
  이슈 링크가 담긴 `**Prior requests:**` 목록이 있어야 한다
- 트리아지 워크플로는 초기에 모든 `.out-of-scope/*.md` 파일을 읽고
  들어오는 이슈를 개념 유사성으로 대조해야 한다

**인수 조건:**
- [ ] 기능을 wontfix로 닫으면 `.out-of-scope/`에 파일이 생성/갱신된다
- [ ] 파일에는 결정, 근거, 닫힌 이슈 링크가 포함된다
- [ ] 일치하는 `.out-of-scope/` 파일이 이미 있으면, 중복 파일을 만들지 않고
      새 이슈를 그 파일의 "Prior requests" 목록에 추가한다
- [ ] 트리아지 중 기존 `.out-of-scope/` 파일을 확인하고, 새 이슈가
      이전 거절과 일치하면 이를 제시한다

**범위 외:**
- 자동 대조 (사람이 일치 여부를 확인함)
- 이전에 거절된 기능 다시 열기
- 버그 보고 (enhancement 거절만 `.out-of-scope/`에 기록됨)
```

### 좋은 에이전트 브리프 (PR)

PR의 경우 "현재 동작"은 diff의 상태를 기술하며, 브리프는 에이전트에게 처음부터 만드는 대신 마무리하거나 고치라고 요청한다.

```markdown
## 에이전트 브리프

**카테고리:** enhancement
**요약:** 기여자가 만든 `triage list`의 `--json` 출력 플래그 마무리

**현재 동작:**
PR은 이슈 목록을 JSON으로 직렬화하는 `--json` 플래그를 추가한다. 정상
경로는 동작하고 diff는 프로젝트의 명령 구조와 맞다. 빈틈이 두 가지
남아 있다. 오류가 여전히 (JSON이 아닌) 사람용 텍스트로 출력되고,
새 플래그에 테스트 커버리지가 없다.

**원하는 동작:**
`--json`을 쓰면 (오류를 포함한) 모든 출력이 stdout에 올바른 JSON으로
나오고, 명령의 종료 코드는 바뀌지 않는다. 플래그가 없을 때 기존
사람용 출력은 그대로다.

**핵심 인터페이스:**
- 명령의 오류 경로는 `--json`일 때 일반 텍스트 오류 대신
  `{ "error": string }`을 출력해야 한다
- PR이 이미 추가한 기존 직렬화기를 재사용한다. 두 번째 것을 만들지 않는다

**인수 조건:**
- [ ] `triage list --json`이 성공과 오류 모두에서 유효한 JSON을 출력한다
- [ ] 종료 코드가 JSON이 아닌 명령과 같다
- [ ] 테스트가 `--json` 성공 출력과 오류 사례 하나를 다룬다
- [ ] 기본(JSON이 아닌) 출력이 바이트 단위로 동일하다

**범위 외:**
- 다른 명령에 `--json` 추가
- PR이 이미 정의한 성공 페이로드의 JSON 형태 변경
```

### 나쁜 에이전트 브리프

```markdown
## 에이전트 브리프

**요약:** 트리아지 버그 수정

**할 일:**
트리아지 쪽이 고장났다. 메인 파일을 보고 고쳐라.
150번째 줄 근처 함수에 문제가 있다.

**변경할 파일:**
- src/triage/handler.ts (line 150)
- src/types.ts (line 42)
```

나쁜 이유:
- 카테고리 없음
- 모호한 설명 ("트리아지 쪽이 고장났다")
- 금방 낡는 파일 경로와 줄 번호 언급
- 인수 조건 없음
- 범위 경계 없음
- 현재 동작과 원하는 동작에 대한 설명 없음
