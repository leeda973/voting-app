# 범위 외(Out-of-Scope) 지식 베이스

저장소의 `.out-of-scope/` 디렉터리는 거절된 기능 요청에 대한 영구 기록을 저장한다. 두 가지 목적이 있다.

1. **조직의 기억**: 기능이 왜 거절되었는지 남겨, 이슈가 닫혀도 그 근거가 사라지지 않게 한다
2. **중복 제거**: 이전 거절과 일치하는 새 이슈가 들어오면, 다시 논쟁하는 대신 스킬이 이전 결정을 제시할 수 있다

## 디렉터리 구조

```
.out-of-scope/
├── dark-mode.md
├── plugin-system.md
└── graphql-api.md
```

이슈마다가 아니라 **개념**마다 파일 하나. 같은 것을 요청하는 여러 이슈는 한 파일 아래에 묶는다.

## 파일 형식

파일은 데이터베이스 항목보다는 짧은 설계 문서처럼, 편안하고 읽기 쉬운 문체로 작성한다. 문단, 코드 샘플, 예시를 활용해 처음 접하는 사람에게도 근거가 명확하고 유용하도록 한다.

```markdown
# 다크 모드

이 프로젝트는 다크 모드나 사용자용 테마 기능을 지원하지 않는다.

## 범위 외인 이유

렌더링 파이프라인은 `ThemeConfig`에 정의된 단일 색상 팔레트를
전제로 한다. 여러 테마를 지원하려면 다음이 필요하다.

- 전체 컴포넌트 트리를 감싸는 테마 컨텍스트 프로바이더
- 컴포넌트별 테마 인식 스타일 해석
- 사용자 테마 설정을 위한 영속성 계층

이는 콘텐츠 작성에 집중하는 프로젝트 방향과 맞지 않는
상당한 아키텍처 변경이다. 테마는 결과물을 임베드하거나
재배포하는 다운스트림 사용자의 관심사다.

```ts
// 현재 ThemeConfig 인터페이스는 런타임 전환을 위해 설계되지 않았다:
interface ThemeConfig {
  colors: ColorPalette; // 단일 팔레트, 빌드 시점에 결정됨
  fonts: FontStack;
}
```

## 이전 요청

- #42: "Add dark mode support"
- #87: "Night theme for accessibility"
- #134: "Dark theme option"
```

### 파일 이름 짓기

개념에 대해 짧고 설명적인 kebab-case 이름을 쓴다: `dark-mode.md`, `plugin-system.md`, `graphql-api.md`. 디렉터리를 훑어보는 사람이 파일을 열지 않고도 무엇이 거절되었는지 알아볼 수 있을 만큼 식별 가능해야 한다.

### 이유 작성하기

이유는 실질적이어야 한다. "원하지 않는다"가 아니라 왜인지를 쓴다. 좋은 이유는 다음을 언급한다.

- 프로젝트 범위나 철학 ("이 프로젝트는 X에 집중한다. 테마는 다운스트림의 관심사다")
- 기술적 제약 ("이를 지원하려면 Y가 필요한데, 이는 우리의 Z 아키텍처와 충돌한다")
- 전략적 결정 ("우리는 B 대신 A를 쓰기로 했다. 왜냐하면...")

이유는 오래 유효해야 한다. 일시적 상황("지금은 너무 바쁘다")은 언급하지 않는다. 그런 것은 진짜 거절이 아니라 보류다.

## `.out-of-scope/`를 확인할 때

트리아지 중(1단계: 맥락 수집) `.out-of-scope/`의 모든 파일을 읽는다. 새 이슈를 평가할 때:

- 요청이 기존 범위 외 개념과 일치하는지 확인한다
- 일치 여부는 키워드가 아니라 개념 유사성으로 판단한다: "night theme"은 `dark-mode.md`와 일치한다
- 일치하면 메인테이너에게 제시한다: "`.out-of-scope/dark-mode.md`와 비슷합니다. 이전에 [이유]로 거절했습니다. 여전히 같은 생각이신가요?"

메인테이너는 다음 중 하나를 할 수 있다.

- **확인**: 새 이슈를 기존 파일의 "이전 요청" 목록에 추가한 뒤 닫는다
- **재고**: 범위 외 파일을 삭제하거나 갱신하고, 이슈는 일반 트리아지를 거친다
- **동의하지 않음**: 이슈들이 관련은 있지만 별개이므로, 일반 트리아지를 진행한다

## `.out-of-scope/`에 기록할 때

**enhancement**(bug가 아님)가 `wontfix`로 *거절*될 때만. 이는 이슈와 똑같이 enhancement PR에도 적용된다. 거절된 PR을 여기에 기록해 같은 요청이 새 코드로 다시 들어오지 않게 한다.

**이미 구현되어** `wontfix`로 닫힌 경우에는 여기에 기록하지 **않는다**. 그것은 거절된 기능이 아니라 구현된 기능이다. 기록하면 중복 확인이 잘못된 거절로 오염된다. 대신 닫는 댓글에서 해당 기능이 이미 어디에 있는지 알려준다.

흐름:

1. 메인테이너가 기능 요청이 범위 외라고 결정한다
2. 일치하는 `.out-of-scope/` 파일이 이미 있는지 확인한다
3. 있으면: 새 이슈를 "이전 요청" 목록에 추가한다
4. 없으면: 개념 이름, 결정, 이유, 첫 번째 이전 요청을 담은 새 파일을 만든다
5. 이슈에 결정을 설명하고 `.out-of-scope/` 파일을 언급하는 댓글을 게시한다
6. `wontfix` 라벨과 함께 이슈를 닫는다

## 범위 외 파일 갱신 또는 삭제

메인테이너가 이전에 거절한 개념에 대해 마음을 바꾸면:

- `.out-of-scope/` 파일을 삭제한다
- 스킬이 예전 이슈를 다시 열 필요는 없다. 그것들은 역사적 기록이다
- 재고를 촉발한 새 이슈는 일반 트리아지를 거친다
