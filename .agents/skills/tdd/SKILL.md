# 테스트 주도 개발

TDD는 red → green 루프다. 이 스킬은 그 루프가 남겨 둘 가치가 있는 테스트를 만들어 내도록 하는 참고 자료다. 좋은 테스트란 무엇인지, 테스트를 어디에 두는지, 안티패턴, 그리고 루프의 규칙을 다룬다. 모든 섹션은 매 사이클마다 적용된다. 루프가 끝난 뒤가 아니라, 루프 전과 루프 도중에 참고하라.

코드베이스를 탐색할 때는 `CONTEXT.md`(있다면)를 읽어 테스트 이름과 인터페이스 용어가 프로젝트의 도메인 언어와 일치하도록 하고, 작업 중인 영역의 ADR을 존중하라.

## 좋은 테스트란

테스트는 구현 세부 사항이 아니라 공개 인터페이스를 통해 동작을 검증한다. 코드는 통째로 바뀔 수 있지만 테스트는 바뀌지 않아야 한다. 좋은 테스트는 명세처럼 읽힌다. "user can checkout with valid cart"는 어떤 기능이 존재하는지 정확히 알려 주며, 내부 구조에 신경 쓰지 않기 때문에 리팩터링에도 살아남는다.

예시는 [tests.md](tests.md), 모킹 가이드라인은 [mocking.md](mocking.md)를 참고하라.

## 심(Seam): 테스트를 두는 곳

**심**(seam)은 테스트하는 공개 경계, 즉 내부로 손을 뻗지 않고 동작을 관찰하는 인터페이스다. 테스트는 심에 두며, 절대 내부 구현을 대상으로 하지 않는다.

**미리 합의한 심에서만 테스트하라.** 테스트를 작성하기 전에 테스트할 심을 적어 두고 사용자와 확인하라. 확인되지 않은 심에는 어떤 테스트도 작성하지 않는다. 모든 것을 테스트할 수는 없으므로, 심을 미리 합의하는 것이 테스트 노력을 모든 엣지 케이스가 아니라 핵심 경로와 복잡한 로직에 집중시키는 방법이다.

이렇게 물어라: "공개 인터페이스는 무엇이고, 어떤 심을 테스트해야 할까요?"

그 인터페이스의 형태 자체가 불확실할 때(모듈이 얼마나 깊은지, 심이 어디에 속하는지, 인터페이스가 무엇을 노출해야 하는지)는 Skill 도구를 "codebase-design"으로 호출해 용어를 참고하라. 이 스킬은 module, interface, depth, seam, adapter, leverage, locality 용어의 공통 출처이며, 세션을 진행하는 것이 아니라 참고하는 자료다.

## 안티패턴

- **구현 결합(Implementation-coupled)**: 내부 협력 객체를 모킹하거나, private 메서드를 테스트하거나, 우회 경로로 검증한다(인터페이스를 쓰지 않고 데이터베이스를 직접 조회하는 식). 징후: 동작은 바뀌지 않았는데 리팩터링하면 테스트가 깨진다.
- **동어반복(Tautological)**: 단언이 코드와 같은 방식으로 기댓값을 다시 계산한다(`expect(add(a, b)).toBe(a + b)`, 같은 방식으로 손으로 만든 스냅샷, 자기 자신과 같다고 단언한 상수). 그래서 구조상 항상 통과하며 코드와 절대 어긋날 수 없다. 기댓값은 독립적인 진실의 원천에서 와야 한다. 검증된 리터럴, 풀어 본 예제, 명세 등이다.
- **수평 슬라이싱(Horizontal slicing)**: 모든 테스트를 먼저 쓰고 나서 모든 구현을 한다. 일괄 작성한 테스트는 _상상한_ 동작을 검증한다. 사용자가 보는 동작이 아니라 사물의 *형태*를 테스트하게 되고, 테스트는 실제 변화에 둔감해지며, 구현을 이해하기도 전에 테스트 구조에 얽매인다. 대신 **수직 슬라이스**(vertical slice)로 작업하라. 테스트 하나 → 구현 하나 → 반복. 각 테스트는 직전 사이클에서 배운 것에 반응하는 **예광탄**(tracer bullet)이다.

## 루프의 규칙

- **green 전에 red.** 실패하는 테스트를 먼저 쓰고, 그것을 통과시킬 만큼만 코드를 작성하라. 앞으로의 테스트를 예상하거나 추측성 기능을 추가하지 마라.
- **한 번에 한 슬라이스.** 사이클마다 심 하나, 테스트 하나, 최소 구현 하나.
- **리팩터링은 루프의 일부가 아니다.** 리팩터링은 red → green 구현 사이클이 아니라 리뷰 단계(`code-review` 스킬 참고)에 속한다.
