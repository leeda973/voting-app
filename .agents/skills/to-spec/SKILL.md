이 스킬은 현재 대화의 맥락과 코드베이스에 대한 이해를 바탕으로 스펙을 만든다. 사용자를 인터뷰하지 마라. 이미 알고 있는 것을 종합하기만 하라.

이슈 트래커와 트리아지 라벨 용어는 이미 제공되었어야 한다. 그렇지 않다면 사용자에게 `/setup-matt-pocock-skills`를 실행하라고 안내하라.

## 절차

1. 아직 하지 않았다면 저장소를 탐색해 코드베이스의 현재 상태를 파악하라. 스펙 전체에서 프로젝트의 도메인 용어집 어휘를 사용하고, 작업 중인 영역의 ADR을 존중하라.

2. 기능을 테스트할 심(seam)의 윤곽을 잡아라. 새로운 심보다 기존 심을 우선하라. 가능한 한 가장 높은 심을 사용하라. 새로운 심이 필요하다면 가능한 가장 높은 지점에서 제안하라. 코드베이스 전체의 심은 적을수록 좋으며, 이상적인 개수는 하나다.

이 심들이 사용자의 기대와 맞는지 확인하라.

3. 아래 템플릿으로 스펙을 작성한 뒤 프로젝트 이슈 트래커에 게시하라. `ready-for-agent` 트리아지 라벨을 붙여라. 추가 트리아지는 필요 없다.

## 구현 결정 사항

내려진 구현 결정의 목록. 다음을 포함할 수 있다:

- 새로 만들거나 수정할 모듈
- 수정될 해당 모듈의 인터페이스
- 개발자가 준 기술적 설명
- 아키텍처 결정
- 스키마 변경
- API 계약
- 구체적인 상호작용

구체적인 파일 경로나 코드 스니펫은 포함하지 마라. 금방 낡아 버릴 수 있다.

예외: 프로토타입이 산문보다 결정을 더 정확하게 담아내는 스니펫(상태 머신, 리듀서, 스키마, 타입 형태)을 만들었다면, 관련 결정 안에 인라인으로 넣고 프로토타입에서 나왔다고 간단히 적어라. 작동하는 데모가 아니라 결정이 풍부한 부분, 즉 중요한 부분만 남기도록 잘라 내라.

## 테스트 결정 사항

내려진 테스트 결정의 목록. 다음을 포함하라:

- 좋은 테스트의 조건에 대한 설명(구현 세부 사항이 아니라 외부 동작만 테스트)
- 테스트할 모듈
- 테스트의 선행 사례(즉, 코드베이스에 있는 유사한 유형의 테스트)
