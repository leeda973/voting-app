# 심화(Deepening)

의존성을 고려하여 얕은 모듈 묶음을 안전하게 심화하는 방법. [SKILL.md](SKILL.md)의 어휘를 전제로 한다: **모듈(module)**, **인터페이스(interface)**, **심(seam)**, **어댑터(adapter)**.

## 의존성 범주

심화 후보를 평가할 때는 그 의존성을 분류하라. 범주에 따라 심화된 모듈을 심 너머로 어떻게 테스트할지가 결정된다.

### 1. 인프로세스(In-process)

순수 계산, 메모리 내 상태, I/O 없음. 항상 심화 가능하다. 모듈들을 합치고 새 인터페이스를 통해 직접 테스트하라. 어댑터가 필요 없다.

### 2. 로컬 대체 가능(Local-substitutable)

로컬 테스트 대역이 있는 의존성(Postgres 대신 PGLite, 메모리 내 파일 시스템). 대역이 존재한다면 심화 가능하다. 심화된 모듈은 테스트 스위트에서 대역을 실행하며 테스트한다. 심은 내부에 있으며, 모듈의 외부 인터페이스에 포트는 없다.

### 3. 원격이지만 소유함(Ports & Adapters)

네트워크 경계 너머에 있는 자체 서비스(마이크로서비스, 내부 API). 심에 **포트(port)** (인터페이스)를 정의하라. 딥 모듈이 로직을 소유하고, 전송 계층은 **어댑터**로 주입된다. 테스트는 메모리 내 어댑터를 사용한다. 프로덕션은 HTTP/gRPC/큐 어댑터를 사용한다.

권고 형태: *"심에 포트를 정의하고, 프로덕션용 HTTP 어댑터와 테스트용 메모리 내 어댑터를 구현하라. 그러면 네트워크를 가로질러 배포되더라도 로직은 하나의 딥 모듈 안에 있게 된다."*

### 4. 진짜 외부(Mock)

통제할 수 없는 서드파티 서비스(Stripe, Twilio 등). 심화된 모듈은 외부 의존성을 주입된 포트로 받고, 테스트는 목(mock) 어댑터를 제공한다.

## 심 규율

- **어댑터가 하나면 가상의 심이다. 어댑터가 둘이면 진짜 심이다.** 최소 두 개의 어댑터(보통 프로덕션 + 테스트)가 정당화되지 않는다면 포트를 도입하지 마라. 어댑터가 하나뿐인 심은 그저 간접 참조일 뿐이다.
- **내부 심 vs 외부 심.** 딥 모듈은 인터페이스에 있는 외부 심뿐 아니라 내부 심(구현에 비공개이며 자체 테스트에서 사용)도 가질 수 있다. 테스트가 사용한다는 이유만으로 내부 심을 인터페이스를 통해 노출하지 마라.

## 테스트 전략: 쌓지 말고 대체하라

- 심화된 모듈의 인터페이스에서 테스트가 생기면, 얕은 모듈에 대한 기존 단위 테스트는 낭비가 된다. 삭제하라.
- 심화된 모듈의 인터페이스에서 새 테스트를 작성하라. **인터페이스가 곧 테스트 표면이다**.
- 테스트는 내부 상태가 아니라 인터페이스를 통해 관찰 가능한 결과를 검증한다.
- 테스트는 구현이 아니라 동작을 기술하므로 내부 리팩터링에서도 살아남아야 한다. 구현이 바뀔 때 테스트도 바뀌어야 한다면, 그 테스트는 인터페이스 너머를 테스트하고 있는 것이다.
