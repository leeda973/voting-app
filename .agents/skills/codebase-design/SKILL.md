# Codebase Design

**딥 모듈(deep module)** 을 설계하라. 작은 인터페이스 뒤에 많은 동작을 두고, 깔끔한 심에 배치하며, 그 인터페이스를 통해 테스트할 수 있게. 코드를 설계하거나 재구성하는 곳이라면 어디서든 이 언어와 원칙을 사용하라. 목표는 호출자에게는 레버리지, 유지 보수자에게는 지역성, 모두에게는 테스트 용이성이다.

## 용어집

이 용어들을 정확히 사용하라. "component", "service", "API", "boundary"로 대체하지 마라. 일관된 언어가 핵심이다.

**모듈(Module)**: 인터페이스와 구현을 가진 모든 것. 의도적으로 규모와 무관하다. 함수, 클래스, 패키지, 또는 여러 계층에 걸친 슬라이스. _피할 것_: unit, component, service.

**인터페이스(Interface)**: 호출자가 모듈을 올바르게 사용하기 위해 알아야 하는 모든 것. 타입 시그니처뿐 아니라 불변 조건, 순서 제약, 오류 모드, 필수 설정, 성능 특성까지. _피할 것_: API, signature (너무 좁다. 타입 수준의 표면만 가리킨다).

**구현(Implementation)**: 모듈 안에 있는 것, 즉 코드 본체. **어댑터**와 구별된다. 어떤 것은 큰 구현을 가진 작은 어댑터(Postgres 저장소)일 수도 있고, 작은 구현을 가진 큰 어댑터(메모리 내 가짜 객체)일 수도 있다. 심이 주제일 때는 "어댑터"를, 그 외에는 "구현"을 써라.

**깊이(Depth)**: 인터페이스에서의 레버리지. 호출자(또는 테스트)가 배워야 하는 인터페이스 단위당 실행할 수 있는 동작의 양. 작은 인터페이스 뒤에 많은 동작이 있으면 모듈이 **깊다(deep)** 고 하고, 인터페이스가 구현만큼 복잡하면 **얕다(shallow)** 고 한다.

**심(Seam)** _(Michael Feathers)_: 그 자리를 수정하지 않고도 동작을 바꿀 수 있는 곳. 모듈의 인터페이스가 존재하는 *위치*. 심을 어디에 둘지는 그 뒤에 무엇을 둘지와는 별개인 독자적인 설계 결정이다. _피할 것_: boundary (DDD의 bounded context와 의미가 겹친다).

**어댑터(Adapter)**: 심에서 인터페이스를 충족하는 구체적인 것. 실체(안에 무엇이 있는지)가 아니라 *역할*(어떤 자리를 채우는지)을 나타낸다.

**레버리지(Leverage)**: 호출자가 깊이로부터 얻는 것. 배우는 인터페이스 단위당 더 많은 능력. 하나의 구현이 N개의 호출 지점과 M개의 테스트에 걸쳐 보답한다.

**지역성(Locality)**: 유지 보수자가 깊이로부터 얻는 것. 변경, 버그, 지식, 검증이 호출자들에게 퍼지지 않고 한곳에 집중된다. 한 번 고치면 모든 곳이 고쳐진다.

## 깊음 vs 얕음

**딥 모듈** = 작은 인터페이스 + 많은 구현:

```
┌─────────────────────┐
│   Small Interface   │  ← 적은 메서드, 단순한 매개변수
├─────────────────────┤
│                     │
│  Deep Implementation│  ← 복잡한 로직이 숨겨짐
│                     │
└─────────────────────┘
```

**얕은 모듈** = 큰 인터페이스 + 적은 구현 (피하라):

```
┌─────────────────────────────────┐
│       Large Interface           │  ← 많은 메서드, 복잡한 매개변수
├─────────────────────────────────┤
│  Thin Implementation            │  ← 그냥 통과시킬 뿐
└─────────────────────────────────┘
```

인터페이스를 설계할 때 물어보라:

- 메서드 수를 줄일 수 있는가?
- 매개변수를 단순화할 수 있는가?
- 더 많은 복잡성을 안에 숨길 수 있는가?

## 원칙

- **깊이는 구현이 아니라 인터페이스의 속성이다.** 딥 모듈은 내부적으로 작고, 목 처리 가능하고, 교체 가능한 부품들로 구성될 수 있다. 다만 그것들이 인터페이스의 일부가 아닐 뿐이다. 모듈은 인터페이스에 있는 **외부 심** 뿐 아니라 **내부 심** (구현에 비공개이며 자체 테스트에서 사용)도 가질 수 있다.
- **삭제 테스트.** 모듈을 삭제한다고 상상해 보라. 복잡성이 사라진다면 그것은 통과용이었다. 복잡성이 N개의 호출자에 걸쳐 다시 나타난다면 제 몫을 하고 있던 것이다.
- **인터페이스가 곧 테스트 표면이다.** 호출자와 테스트는 같은 심을 가로지른다. 인터페이스 *너머*를 테스트하고 싶다면, 아마 모듈의 형태가 잘못된 것이다.
- **어댑터가 하나면 가상의 심이다. 어댑터가 둘이면 진짜 심이다.** 심을 가로질러 실제로 무언가가 달라지지 않는다면 심을 도입하지 마라.

## 테스트 용이성을 위한 설계

좋은 인터페이스는 테스트를 자연스럽게 만든다:

1. **의존성을 만들지 말고 받아라.**

   ```typescript
   // 테스트 가능
   function processOrder(order, paymentGateway) {}

   // 테스트하기 어려움
   function processOrder(order) {
     const gateway = new StripeGateway();
   }
   ```

2. **부수 효과를 만들지 말고 결과를 반환하라.**

   ```typescript
   // 테스트 가능
   function calculateDiscount(cart): Discount {}

   // 테스트하기 어려움
   function applyDiscount(cart): void {
     cart.total -= discount;
   }
   ```

3. **작은 표면적.** 메서드가 적을수록 필요한 테스트도 적다. 매개변수가 적을수록 테스트 준비가 단순하다.

## 관계

- **모듈**은 정확히 하나의 **인터페이스**(호출자와 테스트에게 보여 주는 표면)를 가진다.
- **깊이**는 **모듈**의 속성이며, 그 **인터페이스**를 기준으로 측정된다.
- **심**은 **모듈**의 **인터페이스**가 존재하는 곳이다.
- **어댑터**는 **심**에 위치하며 **인터페이스**를 충족한다.
- **깊이**는 호출자에게 **레버리지**를, 유지 보수자에게 **지역성**을 만들어 낸다.

## 기각된 관점

- **구현 줄 수 대 인터페이스 줄 수의 비율로서의 깊이** (Ousterhout): 구현을 부풀리는 것에 보상을 준다. 우리는 대신 레버리지로서의 깊이를 사용한다.
- **TypeScript `interface` 키워드나 클래스의 public 메서드로서의 "인터페이스"**: 너무 좁다. 여기서 인터페이스는 호출자가 알아야 하는 모든 사실을 포함한다.
- **"Boundary"**: DDD의 bounded context와 의미가 겹친다. **심**이나 **인터페이스**라고 말하라.
