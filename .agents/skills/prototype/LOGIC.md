# 로직 프로토타입

누구나 버튼을 클릭해 상태 모델을 조작할 수 있게 해 주는, 자체 완결형 HTML 파일 하나(**공유 가능한 데모**)입니다. 질문이 **비즈니스 로직, 상태 전이, 데이터 형태**에 관한 것일 때 사용하세요. 종이 위에서는 그럴듯해 보이지만 실제 사례로 밀어붙여 봐야 비로소 잘못됐다는 느낌이 드는 종류의 것들입니다.

설치할 것 없는 파일 하나이므로, 개발자가 아닌 사람(디자이너, PM, 도메인 전문가)에게 건네 직접 모델을 체감하게 할 수 있습니다. 그러니 코드의 언어가 아니라 그들의 언어로 말해야 합니다.

## 이 형태가 맞는 경우

- "이 상태 머신이 X 다음에 Y가 일어나는 엣지 케이스를 처리하는지 잘 모르겠어요."
- "이 데이터 모델로 정말 ...한 경우를 표현할 수 있나요?"
- "API를 작성하기 전에 어떤 모습이어야 할지 감을 잡고 싶어요."
- 누군가가 **버튼을 누르고 상태가 바뀌는 것을 지켜보고** 싶어 하는 모든 경우.

질문이 "이것은 어떤 모습이어야 하는가"라면 이 갈래는 맞지 않습니다. [UI.md](UI.md)를 사용하세요.

## 절차

### 1. 질문 명시하기

코드를 작성하기 전에, 어떤 상태 모델과 어떤 질문을 프로토타이핑하는지 적으세요. 데모 맨 위에(주석만이 아니라 눈에 보이는 소개 부분에) 한 문단으로 적습니다. 잘못된 질문에 답하는 로직 프로토타입은 순전히 낭비이므로, 사용자가 지금 지켜보고 있든 자리를 비웠다가(AFK) 나중에 돌아오든 확인할 수 있도록 질문을 명시하세요.

### 2. 로직을 이식 가능한 module로 분리하기

실제 로직(질문에 답하는 부분)은 하나의 `<script>` 블록 안에, 나중에 떼어 내 실제 코드베이스에 넣을 수 있는 작고 순수한 module로 작성하세요. 그 주변의 페이지는 버릴 것이지만, 이 module은 그렇지 않습니다.

적절한 형태는 질문에 따라 다릅니다.

- **순수 리듀서(reducer)**: `(state, action) => state`. 액션이 개별 이벤트이고 상태가 단일 값일 때 적합합니다.
- **상태 머신**: 명시적인 상태와 전이. "지금 어떤 액션이 허용되는가"가 질문의 일부일 때 적합합니다.
- 평범한 데이터 타입에 대한 **작은 순수 함수 집합**. 암묵적인 현재 상태 없이 변환만 있을 때 적합합니다.
- 로직이 실제로 지속적인 내부 상태를 소유할 때는 **명확한 메서드 표면을 가진 클래스나 module**.

페이지에 연결하기 가장 쉬운 형태가 _아니라_, 묻고 있는 질문에 가장 잘 맞는 형태를 고르세요. 순수하게 유지하세요. DOM도, `document`도, 그 안으로 파고드는 버튼 핸들러도 없어야 합니다. 페이지가 module을 호출할 뿐, 반대 방향으로는 아무것도 흐르지 않습니다. 이것이 프로토타입을 그 수명 이후에도 유용하게 만드는 점입니다. 질문에 답이 나오면, 검증된 리듀서 / 머신 / 함수 집합은 그대로 실제 module로 옮겨집니다.

### 3. 공유 가능한 HTML 파일 만들기

파일 하나, 평범한 HTML/CSS/JS로 만드세요. 프레임워크도, 번들러도, 서버도 없이 모든 것을 인라인으로 넣어, 더블클릭으로 열리고 이메일로 돌려도 문제없게 하세요. 누구나 파일을 여는 것만으로 실행할 수 있어야 합니다.

개발자가 아닌 사람을 위해 작성하세요. 모든 레이블은 코드가 아니라 **도메인 언어**로 씁니다. 버튼과 상태는 리듀서가 아니라 비즈니스처럼 읽혀야 합니다. 무슨 일이 일어나고 있는지 쉬운 말로 설명하세요.

위에서 아래로, 깔끔한 계층 구조로 배치하세요.

1. 이 데모로 무엇을 탐색할 수 있는지(1단계의 질문)에 대한 **제목과 한 줄 설명**.
2. **현재 상태**: 관련 상태 전체를 읽기 쉬운 패널(원시 JSON 덤프가 아니라 레이블이 붙은 필드)로 렌더링하고, 변화가 보이도록 클릭할 때마다 다시 렌더링합니다. 개발자가 아닌 사람이 따라가는 데 도움이 된다면 방금 무엇이 바뀌었는지 표시하세요.
3. **자유 조작 버튼**: 액션마다 버튼 하나씩, 항상 사용 가능하게 두어 누구나 어떤 순서로든 모델을 건드려 볼 수 있게 합니다. 클릭할 때마다 해당 액션을 디스패치하고 상태를 다시 렌더링합니다.
4. **가이드 워크스루**: 탭마다 하나씩 있는 **시나리오** 집합. 각 탭에는 시나리오에 대한 짧고 쉬운 설명(어떤 상황을 설정하는지, 무엇을 지켜봐야 하는지)이 있고, 그 아래에 해당 시나리오에서 순서대로 **눌러야 할 버튼**이 있습니다. 각 단계는 실제 버튼입니다. 클릭하면 그 액션을 수행하고 다음 단계로 넘어갑니다. 워크스루를 시작하면 알려진 초기 상태로 초기화되어, 시나리오가 매번 똑같이 진행됩니다.

종이 위에서는 따져 보기 어려운 곤란한 경우를 보여 주는 시나리오를 고르세요. 정상 경로(happy path), 까다로운 엣지 케이스, 허용되지 않아야 할 무언가를 시도하는 경우 등입니다.

아름답되 절제되게 유지하세요. 깔끔한 타이포그래피, 넉넉한 간격, 강조색 하나. 애니메이션도, 눈속임도 없이, 상태와 버튼과 경쟁하는 것은 아무것도 두지 마세요.

### 4. 전달하기

파일을 보내거나 직접 열어 주세요. 사용자는 시간이 날 때 워크스루를 클릭해 보고 자유롭게 조작해 볼 것입니다. 흥미로운 순간은 사용자가 "잠깐, 이건 불가능해야 하는데" 또는 "어, X는 다를 줄 알았는데"라고 말할 때입니다. 그것이 _아이디어_의 버그이며, 바로 그것이 핵심입니다. 새 액션이나 새 시나리오를 원하면 추가하세요. 프로토타입은 진화합니다.

### 5. 답과 프로토타입 기록하기

프로토타입이 질문에 답을 내면 답을 기록하고, [SKILL](SKILL.md)에 설명된 방식으로 프로토타입을 기록으로 남기세요. 로직에 특화된 대응 관계는 다음과 같습니다. 검증된 리듀서 / 머신 / 함수 집합은 실제 module로 옮겨지고(결정이 흡수됨), HTML 껍데기는 프로토타입을 1차 자료로 보관하는 버리는 용도의 브랜치로 함께 갑니다. 자체 완결형 파일 하나이므로 그곳에서도 언제든 쉽게 다시 실행할 수 있습니다.

## 안티패턴

- **테스트를 추가하지 마세요.** 테스트가 필요한 프로토타입은 더 이상 프로토타입이 아닙니다.
- **실제 데이터베이스에 연결하지 마세요.** 질문이 구체적으로 영속화에 관한 것이 아니라면 메모리 내 상태를 사용하세요.
- **일반화하지 마세요.** "나중에 X를 지원하고 싶으면 어쩌지"는 없습니다. 프로토타입은 하나의 질문에 답합니다.
- **로직과 페이지를 뒤섞지 마세요.** 순수 module이 DOM, `document`, 버튼 핸들러를 참조하면 더 이상 떼어 낼 수 없습니다. 페이지는 순수 module 위의 얇은 껍데기로 유지하세요.
- **프레임워크, 번들러, 서버에 손대지 마세요.** 받는 사람이 더블클릭하는 파일 하나여야 합니다. React 앱이나 개발 서버는 "공유 가능"이라는 목적을 무너뜨립니다.
- **HTML 껍데기를 프로덕션에 배포하지 마세요.** 페이지는 손으로 클릭해 보는 데 최적화되어 있습니다. 그 뒤의 로직 module이 남길 가치가 있는 부분입니다.
