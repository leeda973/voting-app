# UI 프로토타입

하나의 라우트에서 하단 플로팅 바로 전환할 수 있는 **근본적으로 서로 다른 여러 UI 변형**을 생성하세요. 사용자는 브라우저에서 변형들을 넘겨 보며 하나를 고르고(또는 각각에서 일부를 가져오고), 나머지는 버립니다.

질문이 무언가의 생김새가 아니라 로직/상태에 관한 것이라면 이 갈래는 맞지 않습니다. [LOGIC.md](LOGIC.md)를 사용하세요.

## 이 형태가 맞는 경우

- "이 페이지는 어떤 모습이어야 할까요?"
- "확정하기 전에 이 대시보드의 몇 가지 안을 보고 싶어요."
- "설정 화면에 다른 레이아웃을 시도해 보세요."
- 그렇지 않으면 사용자가 머릿속의 모호한 목업 세 개 중에서 고르느라 하루를 보낼 모든 경우.

## 두 가지 하위 형태: 하위 형태 A를 강력히 권장

UI 프로토타입은 **앱의 나머지 부분과 맞닿아 있을 때** 훨씬 판단하기 쉽습니다. 실제 헤더, 실제 사이드바, 실제 데이터, 실제 밀도가 있을 때 말이죠. 단독으로 떨어진 버리는 용도의 라우트는 진공 상태와 같아서, 고립된 상태에서는 모든 변형이 괜찮아 보입니다. 변형을 담을 만한 기존 페이지가 있다면 언제나 하위 형태 A를 기본으로 하세요. 프로토타입이 정말로 근처에 둘 곳이 없을 때만 하위 형태 B를 사용하세요.

### 하위 형태 A: 기존 페이지 조정 (권장)

라우트가 이미 존재합니다. 변형은 `?variant=` URL 검색 파라미터로 제어되며 **같은 라우트에서** 렌더링됩니다. 기존 데이터 페칭, 파라미터, 인증은 모두 그대로 둡니다. 렌더링만 교체됩니다. 이것이 기본값이며, 특별한 이유가 없다면 이것을 고르세요.

프로토타입 대상이 아직 페이지는 없지만 *자연스럽게 어떤 페이지 안에 들어갈* 것(대시보드의 새 섹션, 설정 화면의 새 카드, 기존 흐름의 새 단계)이라면 여전히 하위 형태 A입니다. 호스트 페이지 안에 변형들을 마운트하세요.

### 하위 형태 B: 새 페이지 (최후의 수단)

프로토타이핑 대상이 정말로 들어갈 기존 페이지가 없을 때만 사용하세요(예: 완전히 새로운 최상위 화면, 또는 어디에도 적절히 끼워 넣을 수 없는 흐름).

프로젝트가 이미 사용하는 라우팅 규칙에 따라 **버리는 용도의 라우트**를 만드세요. 새로운 최상위 구조를 만들어 내지 마세요. 누가 봐도 프로토타입임을 알 수 있게 이름을 지으세요(예: 경로나 파일 이름에 `prototype`이라는 단어 포함). `?variant=` 패턴은 동일합니다.

하위 형태 B로 확정하기 전에 점검하세요. 이것을 끼워 넣을 기존 페이지가 정말 없나요? 빈 라우트는 데이터가 채워진 라우트라면 드러났을 설계 문제를 숨깁니다.

두 하위 형태 모두에서 하단 플로팅 바는 동일합니다.

## 절차

### 1. 질문을 명시하고 N 정하기

기본값은 **변형 3개**입니다. 5개를 넘으면 근본적으로 다르다기보다 잡음이 되기 시작하므로, 5개를 상한으로 하세요.

프로토타입 위치나 파일 맨 위 주석에 계획을 한 줄로 적으세요.

> "기존 `/settings` 라우트에서 `?variant=`로 전환할 수 있는 설정 페이지 변형 3개."

이렇게 하면 사용자가 곁에서 이의를 제기할 수 있든 없든 잘 작동합니다.

### 2. 근본적으로 다른 변형 생성하기

각 변형의 초안을 만드세요. 각각 다음을 지키게 하세요.

- 페이지의 목적과 페이지가 접근할 수 있는 데이터.
- 프로젝트의 컴포넌트 라이브러리 / 스타일링 시스템(TailwindCSS, shadcn, MUI, plain CSS 등 무엇이든).
- 명확한 export 컴포넌트 이름, 예: `VariantA`, `VariantB`, `VariantC`.

변형은 **구조적으로 달라야** 합니다. 색만 다른 것이 아니라 레이아웃, 정보 계층, 주요 어포던스(affordance)가 달라야 합니다. 살짝 손본 카드 그리드 세 개는 UI 프로토타입이 아니라 벽지일 뿐입니다. 두 초안이 너무 비슷하게 나오면, "카드 그리드를 사용하지 말 것"이라는 명시적인 지침을 주고 하나를 다시 만드세요.

### 3. 하나로 연결하기

라우트에 단일 전환 컴포넌트를 만드세요.

```tsx
// 의사 코드, 프로젝트의 프레임워크에 맞게 조정할 것
const variant = searchParams.get('variant') ?? 'A';
return (
  <>
    {variant === 'A' && <VariantA {...data} />}
    {variant === 'B' && <VariantB {...data} />}
    {variant === 'C' && <VariantC {...data} />}
    <PrototypeSwitcher variants={['A','B','C']} current={variant} />
  </>
);
```

하위 형태 A(기존 페이지)의 경우: 기존 데이터 페칭은 모두 전환 컴포넌트 위에 두고, 변형마다 렌더링되는 하위 트리만 바뀌게 하세요.

하위 형태 B(새 페이지)의 경우: `/prototype/<name>` 아래의 버리는 용도의 라우트가 같은 전환 컴포넌트를 마운트합니다.

### 4. 플로팅 전환 바 만들기

화면 하단 중앙에 고정 위치로 놓이는 작은 바로, 세 부분으로 구성됩니다.

- **왼쪽 화살표**: 이전 변형으로 순환합니다(끝에서 처음으로 돌아감).
- **변형 레이블**: 현재 변형 키와, 변형이 이름을 export한다면 그 이름도 표시합니다. 예: `B (Sidebar layout)`.
- **오른쪽 화살표**: 다음 변형으로 순환합니다(끝에서 처음으로 돌아감).

동작:

- 화살표를 클릭하면 URL 검색 파라미터를 업데이트해(프레임워크의 라우터 사용, 예: Next에서는 `router.replace`, React Router에서는 `navigate` 등) 변형을 공유할 수 있고 새로고침해도 유지되게 합니다.
- 키보드: `←`와 `→` 방향키로도 순환합니다. `<input>`, `<textarea>`, `[contenteditable]`에 포커스가 있을 때는 방향키를 가로채지 마세요.
- 평가 중인 디자인의 일부가 아님이 분명하도록 페이지와 시각적으로 구분되게 합니다(예: 고대비 알약 모양, 은은한 그림자).
- 프로덕션 빌드에서는 숨깁니다: `process.env.NODE_ENV !== 'production'` 또는 동등한 검사로 제어해서, 실수로 병합된 프로토타입이 사용자에게 바를 배포하지 않게 합니다.

두 하위 형태 모두 재사용할 수 있도록 전환 바를 하나의 공유 컴포넌트로 만드세요. 프로젝트에서 공유 UI가 있는 곳에 두세요.

### 5. 전달하기

URL(그리고 `?variant=` 키들)을 알려 주세요. 사용자는 시간이 날 때 넘겨 볼 것입니다. 흥미로운 피드백은 대개 **"B의 헤더에 C의 사이드바를 쓰고 싶어요"** 같은 것이며, 그것이 사용자가 실제로 원하는 디자인입니다.

### 6. 답을 기록하고 정리하기

어떤 변형이 선택되면 답(어떤 변형이며 왜인지)을 기록하고, [SKILL](SKILL.md)에 설명된 방식으로 프로토타입을 기록으로 남기세요. 선택된 변형은 실제 코드에 반영하고, 나머지는 main이 아니라 버리는 용도의 브랜치로 옮기세요.

- **하위 형태 A**: 선택된 변형을 기존 페이지에 반영하고, 선택되지 않은 변형과 전환 바는 main에서 제거합니다.
- **하위 형태 B**: 선택된 변형을 실제 라우트로 승격하고, 버리는 용도의 라우트와 전환 바는 main에서 제거합니다.

변형 전체가 1차 자료이므로 쓰레기통이 아니라 버리는 용도의 브랜치에 남깁니다. main 브랜치에 남겨 둔 변형 컴포넌트와 전환 바는 금방 낡고 다음에 읽는 사람을 혼란스럽게 하기 때문입니다.

## 안티패턴

- **색이나 문구만 다른 변형.** 그것은 미세 조정이지 프로토타입이 아닙니다. 진짜 변형은 구조에 대해 서로 다른 의견을 냅니다.
- **변형 간에 코드를 너무 많이 공유하기.** 공유 `<Header>`는 괜찮지만, 공유 `<Layout>`은 목적을 무너뜨립니다. 각 변형은 레이아웃을 자유롭게 버릴 수 있어야 합니다.
- **변형을 실제 변경(mutation)에 연결하기.** 읽기 전용 프로토타입이면 충분합니다. 변형이 무언가를 변경해야 한다면 스텁(stub)을 가리키게 하세요. 질문은 "이것은 어떤 모습이어야 하는가"이지 "백엔드가 동작하는가"가 아닙니다.
- **프로토타입을 곧바로 프로덕션으로 승격하기.** 변형 코드는 프로토타입의 제약(테스트 없음, 최소한의 에러 처리) 아래에서 작성되었습니다. 반영할 때는 제대로 다시 작성하세요.
