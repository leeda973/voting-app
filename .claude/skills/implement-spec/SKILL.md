스펙이 주어졌습니다. 이 스펙에는 구현 방법을 기술한 티켓들이 연결되어 있어야 합니다.

목표는 단일 브랜치에서 스펙 전체를 구현하는 PR입니다.

티켓은 단계 목록이 아닙니다. 티켓 간에 블로킹 관계가 있는 **작업 그래프(task graph)**입니다. 즉, 언제나 바로 가져가 작업할 수 있는 티켓들의 **프런티어(frontier)**가 존재합니다.

서브에이전트와 주고받는 소통은 최소한으로 하세요. 주로 **컨텍스트 포인터(context pointer)**, 즉 스펙, 티켓, 리서치 노트, 이전 커밋을 가리키는 방식으로 소통하세요. 포인터로 이미 확인할 수 있는 정보는 중복하지 마세요.

**구현 서브에이전트(implementer subagent)**는 **최대 동시성**을 위해 가능하면 백그라운드에서 실행하세요.

## 단계

1. 스펙과 티켓을 읽으세요. 작업 그래프를 이해할 수 있을 만큼 읽으세요.

2. (선택) **탐색 서브에이전트(exploration subagent)**를 사용해 티켓에 필요한 탐색(관련 코드베이스 파일 또는 외부 문서)을 수행하세요. 탐색 서브에이전트가 파일을 저장할 수 있도록 하세요. 마크다운 노트를 리포지토리 바깥의, 이후 모든 서브에이전트가 접근할 수 있는 디렉터리에 저장해야 합니다. 이렇게 하면 **구현 서브에이전트**가 탐색보다 구현에 집중할 수 있습니다.

3. 브랜치와 draft PR을 만드세요. PR은 스펙 이슈와 티켓들을 'closing'하도록 표시해야 합니다.

4. **구현 서브에이전트**를 사용해 각 티켓을 구현하세요. 각 구현 서브에이전트는 자신만의 worktree에서, 자신만의 브랜치로 작업해야 합니다.

5. **구현 서브에이전트**가 완료되면 **병합 서브에이전트(merger subagent)**로 그 작업을 PR 브랜치에 병합하세요.

6. 이로 인해 작업 가능한 티켓의 **프런티어**가 바뀌면, 새 티켓을 작업할 **구현 서브에이전트**를 추가로 시작하세요. 이렇게 하면 동시성을 최대로 높일 수 있습니다.

7. 모든 티켓이 완료되면 PR 브랜치에서 /code-review를 실행하세요. 코드 리뷰에서 제기된 모든 이슈를 하나의 **구현 서브에이전트**에서 수정하세요.

8. PR을 리뷰 준비 완료(ready for review)로 표시하세요.

9. 모든 **구현 서브에이전트**의 worktree를 정리하세요.
