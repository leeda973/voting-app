# 프로토타입

프로토타입은 **질문에 답하는, 버리는 용도의 코드**입니다. 질문이 형태를 결정합니다.

## 갈래 고르기

사용자의 프롬프트, 주변 코드를 보고, 또는 사용자가 곁에 있다면 직접 물어서 어떤 질문에 답하려는 것인지 파악하세요.

- **"이 로직 / 상태 모델이 적절한가?"** → [LOGIC.md](LOGIC.md). 종이 위에서는 따져 보기 어려운 경우들로 상태 머신을 밀어붙이고, 개발자가 아닌 사람도 조작할 수 있는, 공유 가능한 HTML 파일 하나(자유 조작 버튼과 탭으로 구분된 가이드 워크스루)를 만드세요.
- **"이것은 어떤 모습이어야 하는가?"** → [UI.md](UI.md). 하나의 라우트에서 URL 검색 파라미터와 하단 플로팅 바로 전환할 수 있는, 근본적으로 서로 다른 여러 UI 변형을 생성하세요.

두 갈래는 매우 다른 산출물을 만들어 내므로, 여기서 잘못 고르면 프로토타입 전체가 낭비됩니다. 질문이 정말로 모호하고 사용자에게 연락이 닿지 않는다면, 주변 코드에 더 잘 맞는 갈래를 기본으로 선택하고(백엔드 module → 로직, 페이지나 컴포넌트 → UI) 프로토타입 맨 위에 그 가정을 명시하세요.

## 두 갈래 모두에 적용되는 규칙

1. **처음부터 버릴 코드이며, 그렇다고 분명히 표시할 것.** 맥락이 분명하도록 프로토타입 코드를 실제로 사용될 곳 가까이(프로토타이핑 대상인 module이나 페이지 옆)에 두되, 대충 훑어보는 사람도 프로덕션이 아니라 프로토타입임을 알 수 있도록 이름을 지으세요. 버리는 용도의 UI 라우트는 프로젝트가 이미 사용하는 라우팅 규칙을 따르고, 새로운 최상위 구조를 만들어 내지 마세요.
2. **실행이 아주 쉬울 것.** UI 프로토타입은 프로젝트의 태스크 러너에서 명령 하나로 시작합니다: `pnpm <name>`, `python <path>`, `bun <path>` 등. 로직 데모는 사용자가 더블클릭하는 HTML 파일 하나입니다. 어느 쪽이든 시작하는 데 고민이 필요 없어야 합니다.
3. **기본적으로 영속화하지 않을 것.** 상태는 메모리에 둡니다. 영속화는 프로토타입이 _확인하려는_ 대상이지, 의존해야 할 대상이 아닙니다. 질문이 명시적으로 데이터베이스와 관련되어 있다면, 스크래치 DB나 "PROTOTYPE, wipe me"처럼 이름이 분명한 로컬 파일을 사용하세요.
4. **다듬기는 건너뛸 것.** 테스트 없이, 프로토타입을 _실행 가능하게_ 만드는 데 필요한 것 이상의 에러 처리 없이, 추상화 없이. 요점은 무언가를 빠르게 배우는 것입니다.
5. **상태를 드러낼 것.** 모든 액션 후(로직) 또는 모든 변형 전환 시(UI)마다 관련 상태 전체를 출력하거나 렌더링해서, 사용자가 무엇이 바뀌었는지 볼 수 있게 하세요.
6. **끝나면 기록으로 남길 것.** 검증된 결정은 실제 코드에 반영하고, 프로토타입 자체는 **1차 자료(primary source)**로 남기세요. main이 아닌 버리는 용도의 브랜치에 커밋하고, 구현 이슈에 그 브랜치를 가리키는 컨텍스트 포인터를 남기세요. 답(결론과 그것이 해결한 질문)도 이슈나 커밋에 기록하세요. main 브랜치에는 검증된 결정만 남깁니다.
