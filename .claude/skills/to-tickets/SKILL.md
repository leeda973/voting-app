# 티켓으로 쪼개기

계획, 스펙, 또는 대화를 **티켓** 묶음으로 쪼갠다. 각 티켓은 예광탄(tracer bullet) 방식의 수직 슬라이스이며, 자신을 **차단**(block)하는 티켓들을 선언한다.

이슈 트래커와 트리아지 라벨 용어는 이미 제공되었어야 한다. 그렇지 않다면 사용자에게 `/setup-matt-pocock-skills`를 실행하라고 안내하라.

## 절차

### 1. 맥락 수집

대화 맥락에 이미 있는 것을 바탕으로 작업하라. 사용자가 인자로 참조(스펙 경로, 이슈 번호나 URL)를 넘기면, 가져와서 본문과 댓글 전체를 읽어라.

### 2. 코드베이스 탐색(선택)

아직 코드베이스를 탐색하지 않았다면, 코드의 현재 상태를 파악하기 위해 탐색하라. 티켓 제목과 설명은 프로젝트의 도메인 용어집 어휘를 사용해야 하며, 작업 중인 영역의 ADR을 존중해야 한다.

구현을 쉽게 만들기 위해 코드를 사전 리팩터링(prefactor)할 기회를 찾아라. "변경을 쉽게 만든 다음, 쉬운 변경을 하라."

### 3. 수직 슬라이스 초안 작성

작업을 **예광탄** 티켓으로 쪼개라.

<vertical-slice-rules>

- 각 슬라이스는 모든 계층(스키마, API, UI, 테스트)을 관통하는 좁지만 완전한 경로를 자른다. 한 계층만의 수평 슬라이스가 아니라 수직이어야 한다
- 완료된 슬라이스는 그 자체로 시연하거나 검증할 수 있다
- 각 슬라이스는 새로운 컨텍스트 윈도우 하나에 들어갈 크기다
- 사전 리팩터링은 무엇이든 가장 먼저 한다

</vertical-slice-rules>

각 티켓에 **차단 관계**(blocking edge)를 부여하라. 즉, 이 티켓을 시작하기 전에 완료되어야 하는 다른 티켓들이다. 차단하는 티켓이 없는 티켓은 즉시 시작할 수 있다.

**광범위 리팩터링은 수직 슬라이싱의 예외다.** **광범위 리팩터링**(wide refactor)은 하나의 기계적인 변경(컬럼 이름 변경, 공유 심볼의 타입 변경)인데 그 **영향 반경**(blast radius)이 코드베이스 전체로 퍼져서, 한 번의 수정이 수천 개의 호출 지점을 한꺼번에 깨뜨리고 어떤 수직 슬라이스도 green 상태로 들어갈 수 없는 경우다. 억지로 예광탄에 끼워 넣지 말고 **확장–축소**(expand–contract)로 순서를 잡아라. 먼저 확장: 새 형태를 기존 형태 옆에 추가해 아무것도 깨지지 않게 한다. 그다음 영향 반경에 맞춘 크기의 배치(패키지별, 디렉터리별)로 호출 지점을 옮기는데, 각 배치는 확장 티켓에 의해 차단되는 별도 티켓이며, 기존 형태가 여전히 존재하므로 배치마다 CI가 green으로 유지된다. 마지막으로 축소: 더 이상 호출하는 곳이 없으면 기존 형태를 삭제하며, 이 티켓은 모든 마이그레이션 배치에 의해 차단된다. 배치조차 단독으로 green을 유지할 수 없다면, 순서는 유지하되 배치들이 하나의 통합 브랜치를 공유하게 하고, 모두 최종 통합 및 검증 티켓을 차단하도록 하라. green은 그 티켓에서만 보장된다.

### 4. 사용자에게 확인

제안한 분할을 번호 목록으로 제시하라. 각 티켓마다 다음을 보여 줘라:

- **제목**: 짧고 설명적인 이름
- **차단 요인**: 먼저 완료되어야 하는 다른 티켓(있다면)
- **제공하는 것**: 이 티켓이 작동하게 만드는 엔드투엔드 동작

사용자에게 물어라:

- 세분화 수준이 적절한가? (너무 굵음 / 너무 잘음)
- 차단 관계가 올바른가? 각 티켓이 정말로 자신을 막는 티켓에만 의존하는가?
- 합치거나 더 쪼개야 할 티켓이 있는가?

사용자가 분할을 승인할 때까지 반복하라.

### 5. 설정된 트래커에 티켓 게시

승인된 티켓을 게시하라. **방법**은 `/setup-matt-pocock-skills`가 설정한 트래커에 따라 다르다. 티켓 자체는 어느 쪽이든 같고, 차단 관계의 형태만 달라진다:

- **로컬 파일** → 티켓마다 `.scratch/<feature-slug>/issues/<NN>-<slug>.md` 아래에 파일 하나를 쓰고, 의존 순서대로(차단하는 티켓 먼저) `01`부터 번호를 매긴다. 각 파일의 "차단 요인"에는 의존하는 티켓의 번호/제목을 나열한다. 아래의 티켓별 파일 템플릿을 사용하라. 파일 하나에 티켓 하나이며, 절대 하나의 합친 파일로 만들지 않는다.
- **실제 이슈 트래커(GitHub, Linear, …)** → 각 티켓의 차단 관계가 실제 식별자를 참조할 수 있도록 의존 순서대로(차단하는 티켓 먼저) 티켓마다 이슈 하나를 게시한다. 플랫폼에 네이티브 차단 / 하위 이슈 관계가 있으면 그것을 사용하고, 없으면 각 티켓의 "차단 요인"에 차단하는 이슈들을 적는다. 별도 지시가 없으면 `ready-for-agent` 트리아지 라벨을 붙여라. 티켓은 구조상 에이전트가 가져가 처리할 수 있게 만들어져 있다.

**프런티어**(frontier)를 처리하라. 즉, 차단하는 티켓이 모두 완료된 티켓이다. 순수한 선형 체인이라면 위에서 아래로 진행한다는 뜻이다.

상위(parent) 이슈는 닫거나 수정하지 마라.

<local-ticket-template>

# <NN>: <티켓 제목>

**만들 것:** 이 티켓이 작동하게 만드는 엔드투엔드 동작을 사용자 관점에서 기술한다. 계층별 구현 목록이 아니다.

**차단 요인:** 이 티켓을 막는 티켓들의 번호/제목, 또는 "없음(즉시 시작 가능)".

**Status:** ready-for-agent

- [ ] 인수 기준 1
- [ ] 인수 기준 2

</local-ticket-template>

어느 형태든 구체적인 파일 경로나 코드 스니펫은 피하라. 금방 낡는다. 예외: 프로토타입이 산문보다 결정을 더 정확하게 담아내는 스니펫(상태 머신, 리듀서, 스키마, 타입 형태)을 만들었다면, 인라인으로 넣고 프로토타입에서 나왔다고 간단히 적어라. 작동하는 데모가 아니라 결정이 풍부한 부분, 즉 중요한 부분만 남기도록 잘라 내라.
