# Domain Modeling

설계하면서 프로젝트의 도메인 모델을 능동적으로 구축하고 다듬어라. 이것은 *능동적인* 규율이다. 용어에 이의를 제기하고, 엣지 케이스 시나리오를 만들어 내고, 용어집과 결정이 구체화되는 순간 바로 적어 둔다. (어휘를 얻으려고 `CONTEXT.md`를 그저 *읽는* 것은 이 스킬이 아니다. 그건 어떤 스킬이든 할 수 있는 한 줄짜리 습관이다. 이 스킬은 모델을 소비만 하는 것이 아니라 바꿀 때를 위한 것이다.)

## 파일 구조

대부분의 저장소는 단일 컨텍스트를 가진다:

```
/
├── CONTEXT.md
├── docs/
│   └── adr/
│       ├── 0001-event-sourced-orders.md
│       └── 0002-postgres-for-write-model.md
└── src/
```

루트에 `CONTEXT-MAP.md`가 있다면 저장소는 여러 컨텍스트를 가진다. 맵은 각 컨텍스트가 어디 있는지 가리킨다:

```
/
├── CONTEXT-MAP.md
├── docs/
│   └── adr/                          ← 시스템 전반의 결정
├── src/
│   ├── ordering/
│   │   ├── CONTEXT.md
│   │   └── docs/adr/                 ← 컨텍스트별 결정
│   └── billing/
│       ├── CONTEXT.md
│       └── docs/adr/
```

파일은 느긋하게(lazily) 만들어라. 쓸 내용이 있을 때만. `CONTEXT.md`가 없다면 첫 용어가 확정될 때 만들어라. `docs/adr/`가 없다면 첫 ADR이 필요할 때 만들어라.

## 세션 중에

### 용어집에 비추어 이의 제기하기

사용자가 `CONTEXT.md`의 기존 언어와 충돌하는 용어를 쓰면 즉시 짚어라. "용어집은 'cancellation'을 X로 정의하는데, 지금은 Y를 뜻하시는 것 같아요. 어느 쪽인가요?"

### 모호한 언어 다듬기

사용자가 모호하거나 과적된 용어를 쓰면 정확한 표준 용어를 제안하라. "'account'라고 하셨는데, Customer를 뜻하나요 User를 뜻하나요? 둘은 서로 다른 것입니다."

### 구체적인 시나리오 논의하기

도메인 관계를 논의할 때는 구체적인 시나리오로 스트레스 테스트하라. 엣지 케이스를 파고드는 시나리오를 만들어 내어, 사용자가 개념 간의 경계를 정확히 말하도록 하라.

### 코드와 교차 확인하기

사용자가 무언가가 어떻게 동작하는지 말하면, 코드도 그렇게 되어 있는지 확인하라. 모순을 발견하면 드러내라: "코드는 Order 전체를 취소하는데, 방금 부분 취소가 가능하다고 하셨어요. 어느 쪽이 맞나요?"

### CONTEXT.md를 그 자리에서 갱신하기

용어가 확정되면 바로 그 자리에서 `CONTEXT.md`를 갱신하라. 모아 두었다가 한꺼번에 하지 마라. 생기는 즉시 기록하라. [CONTEXT-FORMAT.md](./CONTEXT-FORMAT.md)의 형식을 사용하라.

`CONTEXT.md`에는 구현 세부 사항이 전혀 없어야 한다. `CONTEXT.md`를 스펙, 메모장, 또는 구현 결정의 저장소로 취급하지 마라. 그것은 용어집이며, 그 이상도 이하도 아니다.

### ADR은 아껴서 제안하기

다음 세 가지가 모두 참일 때만 ADR 작성을 제안하라:

1. **되돌리기 어렵다**: 나중에 마음을 바꾸는 비용이 상당하다
2. **맥락 없이는 의외다**: 미래의 독자가 "왜 이렇게 했지?"라고 궁금해할 것이다
3. **실제 트레이드오프의 결과다**: 진짜 대안들이 있었고, 구체적인 이유로 그중 하나를 골랐다

셋 중 하나라도 빠지면 ADR은 건너뛰어라. [ADR-FORMAT.md](./ADR-FORMAT.md)의 형식을 사용하라.
